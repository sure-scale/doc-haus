# Dashboard components

Reusable dashboard components based on the refined Overview, AI composer,
Setup and widget-catalog designs. This library does not replace the current
Dashboard page. `e2e/dashboard-components.html` is a standalone browser fixture.

## Feed JSON and a live source

The agent supplies a `ComponentDefinition` and a data source. The application
registers the source and handles actions. Components subscribe to its snapshots;
each published update redraws every bound component without reload or remount.
There are no executable expressions, functions or HTML in the JSON.

```tsx
import {
  createDashboardSource, LiveComponent, type ComponentDefinition,
} from "./visual"

// Create once, outside render. A dynamically created source can use any ID.
const practice = createDashboardSource({
  spend: {
    total: 62.22,
    points: [
      { key: "client-a", label: "Example Studio", value: 40 },
      { key: "client-b", label: "Example Bakery", value: 22.22 },
    ],
  },
})
const sources = { practice }
const definition: ComponentDefinition = {
  id: "client-spend",
  kind: "chart",
  frame: { title: "Spend by client", icon: "spend", size: "wide" },
  props: {
    form: "bars", label: "Client spend", format: "money", currency: "USD",
    basis: "Estimated AI spend", period: "This month", showShares: true,
  },
  bindings: {
    points: { source: "practice", path: "/spend/points" },
    total: { source: "practice", path: "/spend/total" },
  },
}

// Inside the app's router and design-system styles:
// <div className="dash"><LiveComponent definition={definition} sources={sources} /></div>
// Whenever a backend/store/WebSocket/SSE event arrives, publish its new snapshot:
practice.publish({ spend: {
  total: 70,
  points: [
    { key: "client-a", label: "Example Studio", value: 45 },
    { key: "client-b", label: "Example Bakery", value: 25 },
  ],
} })
```

A source can be created dynamically for a query, report or filtered dataset. It
must emit the documented component input structure, or use `bindings` to select
fields from its response. Source IDs are registered by the application; they do
not need to be predefined metrics. JSON Pointer uses `/field/0/subfield` and
escapes `/` as `~1`, `~` as `~0`. An empty path selects the complete source.
Bindings replace top-level component props; for example `items`, `points`,
`value` or `config`. Static props supply presentation such as labels and formats.

For an HTTP endpoint generated by an agent:

```ts
const source = createPollingDashboardSource({
  url: "/ingest/dashboard-data/my-query", intervalMs: 5000,
})
const sources = { "my-query": source }
```

This adapter polls while mounted, shares one request between subscribers, aborts
when the last subscriber unmounts, and supports `refresh()`. It requires a
same-origin endpoint, rejects redirects and times out after 15 seconds. For
immediate event-driven updates, use `createDashboardSource()` and `publish()`
from the existing event transport. The component library does not create server
endpoints, run generated code or maintain its own copy of matter data.

## Input catalog

Use `validateComponentData(kind, data)` to check an agent's output before saving.
`LiveComponent` checks it again after resolving live bindings. Exported TypeScript
types specify every field. Unknown or missing sources, malformed values and
source failures render an explicit state rather than invented zeroes. A failed
source retains its last-success timestamp; a later valid update restores the view.

| kind | Data props | Exported view |
| --- | --- | --- |
| `stat` | `value`, `caption`, optional `tag`, `tagTitle`, `note`, `visual` | `StatCard` |
| `chart` | `form`, `label`, `points`, optional `total`, `format`, `currency`, `basis`, `period`, `badge`, `showShares`, `notes` | `ChartCard` |
| `tokens` | `segments: {key,label,value}[]`, optional `total`, `period`, `notes` | `TokenBreakdown` |
| `actions` | `items: ActionTileData[]` | `ActionTiles` |
| `attention` | `rows: AttentionRowData[]` | `AttentionRows` |
| `matters` | `rows: MatterRowData[]` | `MatterRows` |
| `library` | `cards: LibraryCardData[]` | `LibraryCards` |
| `sample` | `items: SamplePreviewData[]` | `SamplePreview` |
| `setup` | `config: SetupChecklistConfig` | `SetupChecklist` |
| `demo` | `config: DemoDataCardConfig`, optional `busy`, `disabled`, `error` | `DemoDataCard` |
| `tabs` | `items: DashboardTabItem[]`, `activeId`, optional `label`, `newDisabled` | `DashboardTabs` |
| `about` | `config: AboutViewConfig` | `AboutView` |
| `composer` | `open`, `request`, optional `config`, `working`, `disabled`, `error` | `AIComposer` |

`chart.form` is `stat`, `line`, `bars`, `list` or `calendar`. Each point has
`label` and finite numeric `value`, with optional `key`, `time`, `detail`.
Dates are Unix milliseconds. Calendar data needs one dated point per local day;
missing days are described as unavailable, not measured zero. Non-stat chart
values must be nonnegative. Counts use integers; percent values are percentage
points (`25` means 25%). Money uses ISO currency codes, default USD. A ranked
view's optional `total` is the full denominator, including omitted rows. With
shares enabled it must be at least the sum of the displayed values. Line and
calendar totals normally come from the source; the renderer can sum supplied
points where that is meaningful. Define the real period in `period`.

Stat `visual` can be a sparkline (`values`, `label`), a spread (`values`,
`average`, `label`, optional format), or a week (`days` with day/cost/label/today).
The discriminant is `type: "sparkline" | "spread" | "week"`. Presentational stat
`value` is formatted text; use a chart of form `stat` for a numeric value with a
shared formatter. Values are never parsed from display strings to compute data.

A tab badge is `{value: 1, total: 5}` for Setup's **1/5**, or `{value: 3}` for a
simple count. Both support an optional accessible `label`. Bind the entire
`items` array to a live source to update all tab counts at once. Badge values are
nonnegative integers; progress values cannot exceed their positive total.

## Actions and layout

`onAction(action, componentId, payload?)` is the application callback, separate
from the JSON. Attention rows pass their row ID; setup/demo cards pass their
configured action ID. Chrome actions are `select-tab` (`{id}`), `new-dashboard`,
`refine-view`, `change-request` (`{value}`), `generate-dashboard`,
`cancel-dashboard`, `stop-dashboard`. The application writes the resulting UI
state back to its source. A live composer requires an action handler before it
can open. Native dialog containment, Escape and focus restoration are built in.

`AdaptiveGrid` accepts `{id,size}` items and a `renderItem(id)` callback. Its
`adaptive` mode stacks natural-height cards in two columns, closing the space
beside a tall chart. `catalog` uses four columns for KPI tiles. Both collapse
responsively, preserve DOM order and resize on live content changes. Wrap it in
`.dash` for its container-query breakpoints. `frame` applies the shared card
heading, icon, tone and size; omit it for tabs and self-contained setup/demo cards.

The optional `SetupTab({context})` composition connects the checklist to the
existing preference, provider, Word and sample APIs. It is separate from these
pure components. Its demo action accurately adds the existing single fictional
sample matter; it does not claim to create a larger demo corpus.

[`example.json`](./example.json) is a complete serializable input example. Its
`sources` object contains sample starting snapshots, not endpoint definitions.
Create one source per ID, then replace each complete snapshot with live values.
When supplying a custom `DashboardSource`, `getSnapshot()` must return the same
snapshot object until data changes, and `subscribe()` must return its cleanup.
Keep the source registry stable between renders; replace a registry entry to
switch that view to a new dynamically created source.
